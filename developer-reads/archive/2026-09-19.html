Google / 2026-09-18 / Safety・Coding Agents・Infra

読む価値: 大規模なコードベースの変更を継続的に走査し、開発者やコード生成システムの近くで脆弱性を検出・修正する運用を紹介しています。

開発者への示唆: AIによる検出は、リリース後の監査だけでなく、変更直後の高速なフィードバックに置くと価値が出ます。検出、修正案、再検証を分け、既存の静的解析やレビューと競合しない境界を決める必要があります。

試すなら: 小さなリポジトリのプルリクエストで試し、真陽性・誤検知・修正受入率・検出から再検証までの時間を記録します。最初はブロックせず助言モードにし、精度を確認してから段階的に強制してください。

開発者への示唆: API仕様を一つの契約として保てば、人向けクライアントとAI開発環境向けのツール面を同じ入力から更新できます。型、ストリーミング、リトライ、ページングを決定的に生成し、AIには境界の外側の作業を任せる分担が堅実です。

試すなら: 自分のOpenAPIを一つ選び、SDKとドキュメントMCPを生成してCIで差分検査します。仕様変更時の破壊的変更、ストリーミング挙動、生成物のライセンスを先に確認してください。

CIワークフローの実行をポリシー化する

GitHub / 2026-09-17 / Safety・Infra・Coding Agents

読む価値: 誰がどのイベントでどのワークフローを起動できるかを、ワークフロー単位で制御し、影響を可視化しながらREST APIで管理できるようになりました。

開発者への示唆: コーディング支援や自動修正がCIを起動する環境では、実行権限をリポジトリ全体の暗黙ルールにしないことが重要です。評価モードで影響を測ってから、特権ワークフローだけを狭く許可する運用に移せます。

試すなら: デプロイ、リリース、シークレット利用のワークフローを棚卸しし、まず評価モードで実行者・イベント・対象ファイルを記録します。フォーク由来の変更と機密情報を扱う処理を分離し、REST APIでポリシーをコード管理してください。

パッケージの自動公開を段階承認へ切り替える

GitHub / 2026-09-18 / Safety・Infra・API

読む価値: 自動処理には公開直前までの段階登録だけを許し、最終公開を保守担当者の二要素認証付き承認に分離するトークン運用が追加されました。

開発者への示唆: ビルドと公開を同じ長寿命資格情報に結び付けず、CIが作る成果物と人が承認するリリースを別の状態として扱えます。供給網対策を導入するときの移行経路としても現実的です。

試すなら: 影響の小さいパッケージ一つで段階登録を導入し、直接公開が拒否されること、承認後のタグ更新、ロールバック手順を確認します。利用するCLIと実行環境の最低バージョンも固定してください。

AWS / 2026-08-28 / Coding Agents・Safety・Infra

読む価値: 依存関係の脆弱性検知、コード変換、ビルド・テスト、PR作成、複数リポジトリへの並列適用を、既存のCI/CDに組み込む手順をコード付きで示します。定期的な大規模改修を、継続処理へ分解する設計例です。

開発者への示唆: 自動変換を信頼する鍵は、変換そのものではなく、変更単位のPR、再実行、テスト、権限、レビューを一つの境界にすることです。非対話実行では、強い権限を先に許可せず、対象パスと実行コマンドを狭く固定します。

試すなら: まず1つの古い依存関係だけを対象に、検知→変換→テスト→PRの流れを隔離ブランチで作り、失敗時の再実行回数、変更差分、レビュー時間を測ります。

AWS / 2026-08-28 / Inference・Infra・API

試すなら: 2つのAZに2コピーを置く最小構成を作り、配置結果、片系停止時の継続性、スケール変更後の再配置、GPU利用率と費用を記録します。

安全性の失敗類型を固定し、自動評価の改善ループを回す

Anthropic / 2026-08-28 / Safety・Evals・Agents

読む価値: 複数の安全性失敗を測る公開ベンチマークに対して、自動化された研究プロセスで改善案を探索し、評価する報告です。安全性を単発のレッドチームではなく、失敗類型・評価器・再現可能な実験の組み合わせとして考えられます。

開発者への示唆: 自社のエージェントでも、拒否漏れ、過剰拒否、誘導、権限逸脱などの失敗カテゴリを先に定義し、変更前後を同じケースで比較するべきです。自動評価のスコアだけで合格にせず、ホールドアウトと人手確認を残します。

試すなら: 代表的な失敗カテゴリを10〜20件の小さな回帰セットにし、プロンプト・ツール権限・モデル設定を一つずつ変えて、成功率、誤検知、コスト、再現性を記録します。

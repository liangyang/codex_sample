コーディングエージェントは「行動単位」で評価する

Google Developers Blog / 2026-09-09 / Coding Agents・Evals・Safety

読む価値: 大規模なエンドツーエンドベンチマークだけでは、スコアが動いた理由を説明できません。曖昧な依頼への確認、変更後の検証、正規リンクの提示など、観測できる行動を高速な小テストとして積み上げる方法が具体的です。

開発者への示唆: プロンプト、ツールスキーマ、モデルを更新するたびに、最終的な文字列一致ではなく中間状態の不変条件を回帰テストにできます。エージェントの改善を「成功率が上がった」だけで判断しないための土台になります。

試すなら: まず10〜20本の行動テストを作り、確認質問、検証コマンド、変更ファイル、根拠リンクを記録します。変更ごとにローカルで実行し、行動テストと本番に近い総合評価を分けて結果を保存してください。

大規模コード移行は翻訳ではなく段階的な再設計

Mistral / 2026-09-09 / Coding Agents・Evals

読む価値: 40,000行のFortran 77を対象に、呼び出し関係で独立モジュールを切り出し、目標アーキテクチャのレビュー、タスク分割、実装・テスト反復、人間によるプルリクエスト確認を繰り返す実例です。

開発者への示唆: 成否をコンパイルだけでなく、移行前後の数値一致で検証する「パリティハーネス」を先に作るのが要点です。完全自律や手作業の一括移行より、文書化とレビューゲートを含む小さな反復の方が、責任範囲を保ちやすくなります。

試すなら: まず代表入力のゴールデンテストと呼び出しグラフを用意し、1モジュール単位で移行します。各タスクに設計レビュー、数値差分、テスト結果、変更理由を必須化し、差分が許容範囲を超えたら次へ進まない運用にしてください。

エージェントの操作権限を組織側で強制する

GitHub Changelog / 2026-09-09 / Agents・Safety・Infra

読む価値: シェル、ファイルの読み書き、ネットワークドメインごとに、禁止・人間の承認・無確認実行を中央管理できるようになりました。ユーザーやワークスペース側の設定、保存済み承認で制限を弱められない点が実運用向けです。

開発者への示唆: エージェントの安全性をプロンプトの注意書きだけに置かず、組織・チームごとのポリシーとして実行境界に落とせます。権限を細かく分ければ、開発速度を維持しながら高リスク操作だけに承認を要求できます。

試すなら: 読み取り、編集、外部通信、破壊的操作を分類し、開発・CI・本番の3ポリシーを作ります。各操作の承認、拒否、監査ログ、緊急停止を再現テストし、ポリシー変更が既存の作業経路を壊していないか確認してください。

長時間タスクの成否を、状態・評価・回復のループで測る

NVIDIA Technical Blog / 2026-08-21 / Agents・Evals

読む価値: コード変更と実行結果を何度も往復する自律システムを、永続状態、ツール、評価、監督の組み合わせとして説明しています。モデルの一発回答では見えない設計論を、最適化と対話型ベンチマークの両方から読めます。

開発者への示唆: 長いタスクでは、何を保存し、どの評価結果を次の試行へ渡し、停滞時にどう方針を変えるかを決める必要があります。評価も最終回答だけでなく、行動数、再実行率、回復時間を含めます。

試すなら: 小さな最適化タスクを20回まで反復できる実験にし、変更履歴、テスト結果、失敗理由、次の仮説を保存する。成功率と無駄な試行数を記録する。

モデル選択を、更新可能なルーティング層として運用する

Microsoft Foundry Blog / 2026-08-21 / Inference・API

読む価値: 推論先の候補、提供地域、更新、品質・コスト・レイテンシの調整を、アプリ本体から分離する考え方を整理しています。モデルの入れ替えでアプリの接続先を毎回書き換えないための視点があります。

開発者への示唆: ルーティングを導入するなら、実際にどの推論先へ送られたか、候補の入れ替えで品質がどう変わったかを追えるようにします。固定の総合スコアではなく、タスク別の受入基準を持ちます。

試すなら: 分類、要約、コード修正の代表ケースを各20件用意し、品質、レイテンシ、費用、失敗率を比較する。候補変更時の回帰評価を必須にする。

エージェントの権限を、指示ではなく実行環境で制限する

Microsoft Apps on Azure Blog / 2026-08-21 / Safety・Infra

読む価値: 自律運用の安全性を、マイクロVM隔離、秘密情報を直接渡さない認証、出力の除去、リスクに応じた承認として実装する例を示しています。プロンプトだけに安全保証を置かない設計を具体化できます。

開発者への示唆: 誤動作や指示の迂回があっても、環境が変更可能範囲を越えさせないことが重要です。副作用の前に、短命の権限、ネットワーク境界、承認、監査、取り消しを通します。

試すなら: 読み取り、検証、変更の3段階に実行環境を分け、各段階の資格情報、ネットワーク、ファイル、外部APIの許可を列挙する。失敗時の隔離と復旧を試す。

会話の文脈を、そのまま開発タスクへ渡す

Microsoft Teams Blog / 2026-08-21 / Coding Agents・Workflow

読む価値: チームの会話にある要件、決定、制約を、開発作業の依頼へつなぐ流れを紹介しています。機能そのものより、文脈を失わずに作業へ渡す設計が参考になります。

開発者への示唆: 会話を入力にする場合は、根拠、未確定の要望、変更範囲、承認者を確定する必要があります。会話履歴をそのまま実行権限に変えず、計画・差分・テスト結果を確認可能な成果物にします。

試すなら: 小さなバグ修正で、会話から抽出した要件、変更計画、差分、テスト結果、承認を1枚の記録にまとめ、抜けた前提を振り返る。
